# 相册与时间录入（v1）

> 前提是实测出来的，不是假设：**照片过 QQ 之后 EXIF 一点不剩**。
> 桌面那三张（`广州学校测试.jpg`、`存图截图1/2.jpg`）读出来 EXIF 全空，无 GPS、无拍摄时间。
> 所以时间和地点 **100% 由用户口述**，程序只负责把它变成能查的结构。

---

## 一、一句话定稿

> 用户发图 → 她追问「哪本相册、记成哪天」→ 用户答 → 写进目录和 EXIF → 入库。
> **目录是真相，EXIF 是派生。**

---

## 二、相册结构

```
media/photos/
├── 全球/<洲>/<国>/<市>/
│   └── 欧洲/德国/柏林/2023-04-29_1200_ab12.jpg
├── 全国/<省>/<市>/
│   └── 陕西/西安/2024-08-27_0200_cd34.jpg
└── 广东/                       ← 用户注册地（可整块换成别的省）
    └── 深圳/南山/2023-04-29_1200_ef56.jpg
```

| 分支 | 层级 | 区县 |
|---|---|---|
| 全球 | 洲 / 国 / 市 | 不做 |
| 全国 | 省 / 市 | **不做** |
| 本地省（默认广东） | 市 / 区 | **做** |

### 直辖市的写法

省=市时**只写一次**，不重复：

```
全国/上海               ✅
全国/上海/上海           ❌ 同一个名字当两级用
全国/上海/浦东新区        ✅ 将来做区级时，区直接挂在市下面
```

北京、天津、重庆同理。三级会带来两个实际问题：前缀检索时同一座城市的数据被劈成两种形状；目录树里出现同名父子，脚本遍历容易多套一层。

**为什么本地省做到区、外地不做**：不是精度偏好，是能力边界。
深圳的"南山""福田"你天天在，张口就来；去趟西安，没人记得住"碑林区"。做了区也没人填，等于空字段。

**顶层用真实名字（广东），不用"本省"**：换注册地时，改名是明确动作，"本省"这个文件夹会骗人。但路由上有别名——用户说"我这儿/本省"，落到当前注册省。

## 三、路由规则（`media/album_resolver.js`）

### 3.1 三条铁律

1. **词典只解决"归位"，不解决"能不能存"。** 词典没有的地名（波尔图），按用户说的建 `全球/未归类/波尔图`，**绝不拒绝**。存图不是知识问答。
2. **说得出区就记区，说不出就停在市，不逼问。**
3. **时间解析不出来就不写时间，不猜"今天"。** 猜出来的时间比没有更糟——它会让"没存到"变成"存错了地方"。

### 3.2 地名归位顺序

```
国名 → 洲/国(/市)          德国柏林  → 全球/欧洲/德国/柏林
区名 → 市/区（本地省才带区） 南山     → 广东/深圳/南山
市名 → 省/市               西安     → 全国/陕西/西安
省名 → 省                  浙江     → 全国/浙江
都没有 → 未归类/<原话>       波尔图   → 全球/未归类/波尔图
```

解析前先剥掉两样东西：**指令词**（收进画廊/相册/存起来…）和 **时间表述**。
不剥的话，"2017年2月4日"会被当成地名（踩过）。

### 3.3 时间写法（全部支持）

| 用户可能说 | 解析成 | 精度 |
|---|---|---|
| `20230429` | 2023-04-29 | day |
| `230429` | 2023-04-29 | day |
| `2023-04-29` / `2023/4/29` | 2023-04-29 | day |
| `2023年4月29日` / `23年4月29日` | 2023-04-29 | day |
| `去年3月15日` / `前年12月1日` | 2025-03-15 / 2024-12-01 | day |
| `3年前 5月20日` | 2023-05-20 | day |
| `5个月前的12日` | 2026-06-12 | day |
| `10天前` / `昨天` / `前天` | 相对今天 | day |
| `4月29日` | 今年 04-29 | day |
| `2023年4月` | 2023-04-01 | **month** |
| `2023年` | 2023-01-01 | **year** |
| 附加时刻 `16:50` / `23点04分` | 覆盖默认 12:00 | — |

**时刻是弹性附加**：默认 `12:00`，说了就用。
**歧义规则**：6/8 位纯数字优先当日期（`230429`），4 位纯数字优先当时刻（`1650`）。

### 3.4 精度为什么重要

EXIF 只能存一个时间点，所以 `2023年4月` 会落成 `2023-04-01`。
但**"4月1日"不是真日期**，如果以后问"4月1日拍了什么"，这张会被误命中。
所以 `precision` 记在同名 sidecar 里（`xxx.json`），搜索时可以用它打折——EXIF 本身没有精度概念，这个损失只能认。

## 四、入库链路

```
QQ 发图（URL）
  ↓ 下载
media/photos/<相册路径>/<YYYY-MM-DD_HHmmss>_<sha1 前8位>.jpg   ← 文件名 = 时间，目录 = 地点
  ↓ 写 EXIF（DateTimeOriginal + DateTime）
  ↓ POST /api/v1/media/import  (multipart, scope_id = 完整相册路径)
SHW 的 captured_at = 真日期
  ↓ sidecar
<同名>.json  记 album / scope_id / precision / 用户原话 / place
```

**scope_id 用完整路径**（`广东/深圳/南山`），不是扁平名——搜索"深圳"时能前缀命中它下面的区。

## 五、交互

### 5.1 两条路都收

| 场景 | 行为 |
|---|---|
| 图 + 文字（`收进画廊 2017年2月4日 23点04分 广东`） | 直接解析入库 |
| 图 无文字 | 追问「哪本相册、记成哪天」 |
| 追问后答不全 | 点名缺什么，给例子 |
| **连续 3 轮说不清** | **拒收**，但留一句「想存的时候再发一次图，或说"收回刚才那张"」 |

### 5.2 回复话术

```
收好了 🐳 收进《广东/深圳/南山》，记作 2023-04-29。
（重复）收好了 🐳 收进《…》，记作 …（这张之前收过，没重复占地方）
（缺地点）还差相册名～ 比如「深圳南山」
（缺日期）还差日期～ 比如「2023年4月29日」
（三轮后）这张我先不收啦，想存的时候再发一次图，或者跟我说「收回刚才那张」🐳
```

**回复里必须复述一遍时间和相册**——这是让她自己核对。家人鲸那句"也对上了"就是这个作用。

## 六、已知限制（交底）

| 限制 | 说明 |
|---|---|
| 精度损失 | 月级/年级只能存成某月 1 号 / 1 月 1 号，靠 sidecar 的 `precision` 区分 |
| 词典不全 | 目前覆盖：33 省 + 主要地级市 + 广东/深圳/广州/珠海/佛山的区。其余按原话建 |
| 直筒子市 | 东莞、中山不设区，街镇直接挂在市下 |
| 歧义地名 | 「南山」既可能是深圳的区，也可能是别处；当前优先本地省 |
| GPS 永久丢失 | QQ 已剥离，且不伪造 |
